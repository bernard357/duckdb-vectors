# Performance workbook

Questions people ask about the performance of `duckdb-vectors`, answered with measured figures first and the explanation after. All figures come from one reference machine, a MacBook Pro M1 (2021), with the embedding model already loaded. They use two kinds of corpus: synthetic ones generated by the benchmark scripts, which anyone can reproduce, and a real corpus of 247 Markdown files of engineering documentation (5,172 chunks), which grounds the numbers in everyday use. Network round-trip figures are engineering estimates and are labelled as such. [How to reproduce these numbers?](#how-to-reproduce-these-numbers) lists the commands.

## How big is the index file?

About __2.4 KB per chunk__ at the default model, so the file stays small next to anything it ships inside:

| Chunks | Database file |
| --- | --- |
| 1,000 | ~4.8 MB |
| 10,000 | ~26 MB |
| 50,000 | ~114 MB |
| 100,000 | ~235 MB |
| 5,172 (the real corpus) | ~17 MB |

The synthetic chunks are ~300 words each, the Markdown chunker's default target. Each chunk stores its text, a `FLOAT[256]` vector (256 × 4 = 1,024 bytes with the default `fastembed:minishlab/potion-multilingual-128M`), an etag, a title, its metadata as JSON, and its entry in the keyword (BM25) index. The vector term grows with the model's dimension: 1,536 bytes at 384 dims, 4,096 bytes at 1,024 dims. Storage grows linearly with chunk count and is never the constraint: even 100,000 chunks fit in a few hundred megabytes, and because the file travels inside the agent's container image there is no separate data tier to provision, secure, or pay for.

## How fast is a query?

__~26 ms (p50) and ~31 ms (p95)__ for a full hybrid `query()` with `top_k=5` over 1,000 chunks, at the default model. Embedding the query takes __~0.3 ms__ of that:

| Slice | Time | Share |
| --- | --- | --- |
| Query embedding | ~0.3 ms | ~1% |
| Hybrid scan (cosine + BM25 + fusion + fetch) | ~25.5 ms | ~99% |

The default model is static: it maps tokens to fixed vectors with no transformer forward pass, so the embed slice is effectively free and latency is almost entirely the scan. The tail stays close to the median because there is no network hop to stall on.

## How does query time grow with the corpus?

Linearly, from a fixed floor of about 20 ms:

| Chunks | Query p50, default model | Query p95, default model | Query p50, scan only (hashing) |
| --- | --- | --- | --- |
| 1,000 | 25.8 ms | 31.4 ms | 19.4 ms |
| 10,000 | 33.7 ms | 35.8 ms | 30.1 ms |
| 50,000 | 68.3 ms | ~170 ms | 73.3 ms |
| 100,000 | 104-108 ms | 110-143 ms | 122.3 ms |

The brute-force cosine scan is the only term that grows with chunk count, at roughly 1 ms per 1,000 chunks; the keyword scan, Reciprocal Rank Fusion, and the fetch of the top chunks form the fixed floor. The hashing column isolates that scan curve with an embedder that costs nothing. Medians are stable across runs; the p95 tail at 50,000 chunks and above varied between runs (140-170 ms), so treat it as indicative.

## How long does a first index take?

__~3.6 s for the real corpus__ (247 files, 5,172 chunks), and ~2.0 s for the synthetic one (250 files, 1,590 chunks), at the default model:

| Corpus | Files | Chunks | First index | File locked |
| --- | --- | --- | --- | --- |
| Real engineering documentation | 247 | 5,172 | 3.6 s | 1.8 s |
| Synthetic (seed 20261103) | 250 | 1,590 | 2.0 s | 0.6 s |

A first index chunks every file, embeds every chunk, writes them, and builds the keyword index. Chunking is fast because one DuckDB connection serves every Markdown file of a run, and writing is fast because each batch is one `DELETE` and one `INSERT` per 5,000 rows rather than two statements per chunk. With the default static model, embedding is cheap too; a contextual model makes embedding the dominant cost (see [Which model and dimension should I choose?](#which-model-and-dimension-should-i-choose)). These figures exclude the one-time downloads of a first launch: the package, the embedding model, and the DuckDB `markdown` and `fts` extensions.

## What does a restart cost?

__~1 s for an unchanged folder, with nothing re-embedded or written__, which is what an MCP server started with `--index` pays on every launch:

| Real corpus (247 files, 5,172 chunks) | Time | Rows written | File locked |
| --- | --- | --- | --- |
| Re-index, unchanged | 1.05 s | 0 | 0.017 s |
| Re-index, one file edited | 1.20 s | 1 | 0.22 s |

The indexer re-reads and re-chunks the folder, compares each chunk's fingerprint (etag) and stored fields with what is in the database, and embeds and writes only what changed. The time is the chunking pass; the database file is locked only for the lookup and the writes, so other sessions sharing it keep querying.

## How fast is search through the MCP server?

__~45 ms per search after the first__, and ~2 s for the first one, which loads the embedding model; `report` takes ~40 ms. Measured over stdio against the real corpus:

| Call | Time |
| --- | --- |
| First `search` (model load) | ~2.1 s |
| Later `search` (median of 15) | ~45 ms, max ~70 ms |
| `report` | ~40 ms |

The server keeps one embedder for its lifetime, so the model loads once, while each call opens and closes its own store. The ~20 ms above an in-process query is the MCP round-trip plus opening the store.

## Can several sessions share one index?

Yes. Measured with two processes querying one database file at once, every query succeeded (15 of 15 each), and so did every query issued while a third process re-indexed (10 of 10). DuckDB lets one process hold a file at a time, so a store connects only when a call needs the file and waits up to `lock_timeout` seconds (default 10, `DUCKDB_VECTORS_LOCK_TIMEOUT`) when another process holds it. Each search holds the file for the length of the call, and an unchanged re-index holds it for about 0.02 s, so sessions wait milliseconds rather than fail.

## How fast is writing from code?

__~4 s for 10,000 chunks and ~20 s for 50,000__, added through `add_texts` in batches of 2,000 (hashing backend, so the figures isolate the writes). The keyword index is not rebuilt per call: writes mark it stale in the database file, and it is rebuilt once, when the store closes or on the first keyword search that finds it stale. That rebuild takes ~0.09 s for 50,000 chunks. Close the store when done writing, so readers find a fresh index; a writer that exits without closing loses nothing, because the next search sees the stale marker and rebuilds.

## Which model and dimension should I choose?

Start with the default, and step up only if relevance on your own corpus falls short. Model choice moves both latency and storage: the cosine scan does work proportional to __dimension × chunk count__, and the file grows linearly with the dimension.

The default, `fastembed:minishlab/potion-multilingual-128M`, is a 256-dimension static [Model2Vec](https://github.com/MinishLab/model2vec) model: it embeds a query in ~0.1-0.3 ms, keeps the file smallest, and serves multilingual documentation. A contextual (transformer) model such as the MiniLM, mpnet, or e5 tiers ranks better on nuanced or ambiguous queries, at the cost of a larger vector, a larger file, a slower scan, and a much slower embed, which then dominates both query time and indexing time.

Measured candidates (embed p50 over 20 iterations; `hit@k` is a small fixed multilingual relevance sanity check, not a full benchmark; produced by `scripts/benchmark_embedders.py`):

| Model | Dimensions | Embed p50 | hit@1 | hit@3 |
| --- | --- | --- | --- | --- |
| `fastembed:minishlab/potion-multilingual-128M` (default) | 256 | 0.1 ms | 0.80 | 1.00 |
| `fastembed:sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | 384 | 4.2 ms | 0.80 | 1.00 |
| `fastembed:sentence-transformers/paraphrase-multilingual-mpnet-base-v2` | 768 | 11.2 ms | 0.80 | 1.00 |
| `fastembed:intfloat/multilingual-e5-large` | 1024 | 35.6 ms | 0.80 | 1.00 |
| `fastembed:BAAI/bge-small-en-v1.5` | 384 | 4.0 ms | 0.80 | 1.00 |
| `fastembed:BAAI/bge-large-en-v1.5` | 1024 | 35.2 ms | 1.00 | 1.00 |
| `hf:onnx-community/Qwen3-Embedding-0.6B-ONNX` | 1024 | 44.1 ms | 1.00 | 1.00 |
| `hf:onnx-community/embeddinggemma-300m-ONNX` | 768 | ~23 ms | 0.80 | 1.00 |

The two `hf:` rows run through the generalized Hugging Face loader. Qwen3-Embedding is a decoder-style export with external weights; at 1,024 dims and ~44 ms it is the slowest and largest option, and the only one to reach `hit@1` 1.00 on the multilingual bank. EmbeddingGemma bakes pooling and its projection heads into the graph, and the loader reads that final output directly; reading the raw backbone instead drops `hit@1` to 0.60. Measure on your own corpus before trading the default's size and speed for a larger model.

## Why brute force, not an ANN index?

Because at this scale an approximate-nearest-neighbour index buys no speed and gives up exact results. Measured over 1,000 chunks with the DuckDB `vss` extension (HNSW, cosine metric), at the earlier 384-dim default, against the exact top-k as ground truth:

| Approach | Vector-ranking p50 | Recall@5 |
| --- | --- | --- |
| Brute-force exact scan | ~30.1 ms | 1.00 |
| HNSW index (`vss` extension) | ~29.6 ms | 0.96 mean, 0.80 worst-case |

The query plan confirmed `HNSW_INDEX_SCAN`, so this was a genuine HNSW path: ~2% faster, within noise, for 4% lower mean recall. HNSW also needs DuckDB's experimental index-persistence flag. Even at 100,000 chunks the exact scan answers in about a tenth of a second, so the default stays exact. The schema is HNSW-ready — a fixed-size `FLOAT[dim]` array column — for anyone who outgrows that range.

## What does the package deliberately leave out?

Two things, both scope choices that keep it small rather than missing features.

__No stemmed, multi-field full-text engine.__ The embedding model is the primary relevance signal, and it already handles paraphrase and synonyms across languages. The keyword signal is a language-agnostic exact-token BM25, with no stemming and no stopwords, present only to catch what vectors miss: acronyms, codes, and identifiers, so a query for `ESRS` finds `ESRS`.

__No re-ranking stage.__ Retrieval returns the fused top-k directly; there is no cross-encoder or LLM re-ranker. A re-ranker adds a second model, possibly a network hop, and latency, for a modest gain the hybrid fusion already covers for the target use case. A harness that needs one is free to add it.

## When is a network vector database the better fit?

When the corpus outgrows what an exact scan serves well, far beyond the hundred-thousand-chunk range measured here. Below that, a hosted vector database pays a network round-trip on every query, an estimated ~10-50 ms same-region and 50-150 ms or more cross-region or on a cold connection, with a long tail, and none of that time does any searching. In-process retrieval answers in ~26 ms at 1,000 chunks and ~105 ms at 100,000, with no hop at all. The sweet spot for `duckdb-vectors` is integrating thousands to tens of thousands of chunks directly into the agent, trading a managed vector service for a file in the image.

## How to reproduce these numbers?

Run the benchmark scripts from the repository root with the project venv. Each prints a table in the format used on this page and can write raw results with `--json`.

```shell
$ .venv/bin/python scripts/benchmark_queries.py                    # query latency and file size at 1k, 10k, 50k, 100k chunks
$ .venv/bin/python scripts/benchmark_queries.py --backend hashing  # the scan curve alone
$ .venv/bin/python scripts/benchmark_indexing.py                   # first index, restart, one-file edit on a synthetic folder
$ .venv/bin/python scripts/benchmark_indexing.py --folder /path/to/your/docs
$ .venv/bin/python scripts/benchmark_embedders.py                  # the model comparison
```

`benchmark_queries.py` builds synthetic indexes of ~300-word chunks drawn from a letter-only vocabulary, so the keyword index holds real tokens. `benchmark_indexing.py` generates its Markdown folder from a fixed seed. The MCP and multi-session figures come from the server's own tests and stdio probes against the real corpus.
