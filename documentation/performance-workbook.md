# Performance workbook

Questions people ask about the performance of `duckdb-vectors`, answered with measured figures first and the explanation after. All figures come from one reference machine, a MacBook Pro M1 (2021), with the embedding model already loaded. They use two kinds of corpus: synthetic ones generated by the benchmark scripts, which anyone can reproduce, and a real corpus of 247 Markdown files of engineering documentation (5,172 chunks), which grounds the numbers in everyday use. Network round-trip figures are engineering estimates and are labelled as such. [How to reproduce these numbers?](#how-to-reproduce-these-numbers) lists the commands.

## How big is the index file?

About __2.4 KB per chunk__ at the default model, so the file stays small next to anything it ships inside:

| Chunks | Database file |
| --- | --- |
| 1,000 | ~4.8 MB |
| 10,000 | ~26 MB |
| 50,000 | ~114 MB |
| 100,000 | ~235 MB |
| 5,172 (the real corpus) | ~17 MB |

The synthetic chunks are ~300 words each, the Markdown chunker's default target. Each chunk stores its text, a `FLOAT[256]` vector (256 × 4 = 1,024 bytes with the default `fastembed:minishlab/potion-multilingual-128M`), an etag, a title, its metadata as JSON, and its entry in the keyword (BM25) index. The vector term grows with the model's dimension: 1,536 bytes at 384 dims, 4,096 bytes at 1,024 dims. Storage grows linearly with chunk count and is never the constraint: even 100,000 chunks fit in a few hundred megabytes, and because the file travels inside the agent's container image there is no separate data tier to provision, secure, or pay for.

## How fast is a query?

__~26 ms (p50) and ~31 ms (p95)__ for a full hybrid `query()` with `top_k=5` over 1,000 chunks, at the default model. Embedding the query takes __~0.3 ms__ of that:

| Slice | Time | Share |
| --- | --- | --- |
| Query embedding | ~0.3 ms | ~1% |
| Hybrid scan (cosine + BM25 + fusion + fetch) | ~25.5 ms | ~99% |

The default model is static: it maps tokens to fixed vectors with no transformer forward pass, so the embed slice is effectively free and latency is almost entirely the scan. The tail stays close to the median because there is no network hop to stall on.

## How does query time grow with the corpus?

Linearly, from a fixed floor of about 20 ms:

| Chunks | Query p50, default model | Query p95, default model | Query p50, scan only (hashing) |
| --- | --- | --- | --- |
| 1,000 | 25.8 ms | 31.4 ms | 19.4 ms |
| 10,000 | 33.7 ms | 35.8 ms | 30.1 ms |
| 50,000 | 68.3 ms | ~170 ms | 73.3 ms |
| 100,000 | 104-108 ms | 110-143 ms | 122.3 ms |

The brute-force cosine scan is the only term that grows with chunk count, at roughly 1 ms per 1,000 chunks; the keyword scan, Reciprocal Rank Fusion, and the fetch of the top chunks form the fixed floor. The hashing column isolates that scan curve with an embedder that costs nothing. Medians are stable across runs; the p95 tail at 50,000 chunks and above varied between runs (140-170 ms), so treat it as indicative.

## How long does a first index take?

__~3.6 s for the real corpus__ (247 files, 5,172 chunks), and ~2.0 s for the synthetic one (250 files, 1,590 chunks), at the default model:

| Corpus | Files | Chunks | First index | File locked |
| --- | --- | --- | --- | --- |
| Real engineering documentation | 247 | 5,172 | 3.6 s | 1.8 s |
| Synthetic (seed 20261103) | 250 | 1,590 | 2.0 s | 0.6 s |

A first index chunks every file, embeds every chunk, writes them, and builds the keyword index. Chunking is fast because one DuckDB connection serves every Markdown file of a run, and writing is fast because each batch is one `DELETE` and one `INSERT` per 5,000 rows rather than two statements per chunk. With the default static model, embedding is cheap too; a contextual model makes embedding the dominant cost (see [Which model and dimension should I choose?](#which-model-and-dimension-should-i-choose)). These figures exclude the one-time downloads of a first launch: the package, the embedding model, and the DuckDB `markdown` and `fts` extensions.

## What does a restart cost?

__~1 s for an unchanged folder, with nothing re-embedded or written__, which is what an MCP server started with `--index` pays on every launch:

| Real corpus (247 files, 5,172 chunks) | Time | Rows written | File locked |
| --- | --- | --- | --- |
| Re-index, unchanged | 1.05 s | 0 | 0.017 s |
| Re-index, one file edited | 1.20 s | 1 | 0.22 s |

The indexer re-reads and re-chunks the folder, compares each chunk's fingerprint (etag) and stored fields with what is in the database, and embeds and writes only what changed. The time is the chunking pass; the database file is locked only for the lookup and the writes, so other sessions sharing it keep querying.

## How fast is search through the MCP server?

__~45 ms per search after the first__, and ~2 s for the first one, which loads the embedding model; `report` takes ~40 ms. Measured over stdio against the real corpus:

| Call | Time |
| --- | --- |
| First `search` (model load) | ~2.1 s |
| Later `search` (median of 15) | ~45 ms, max ~70 ms |
| `report` | ~40 ms |

The server keeps one embedder for its lifetime, so the model loads once, while each call opens and closes its own store. The ~20 ms above an in-process query is the MCP round-trip plus opening the store.

## Can several sessions share one index?

Yes. Measured with two processes querying one database file at once, every query succeeded (15 of 15 each), and so did every query issued while a third process re-indexed (10 of 10). DuckDB lets one process hold a file at a time, so a store connects only when a call needs the file and waits up to `lock_timeout` seconds (default 10, `DUCKDB_VECTORS_LOCK_TIMEOUT`) when another process holds it. Each search holds the file for the length of the call, and an unchanged re-index holds it for about 0.02 s, so sessions wait milliseconds rather than fail.

## How fast is writing from code?

__~4 s for 10,000 chunks and ~20 s for 50,000__, added through `add_texts` in batches of 2,000 (hashing backend, so the figures isolate the writes). The keyword index is not rebuilt per call: writes mark it stale in the database file, and it is rebuilt once, when the store closes or on the first keyword search that finds it stale. That rebuild takes ~0.09 s for 50,000 chunks. Close the store when done writing, so readers find a fresh index; a writer that exits without closing loses nothing, because the next search sees the stale marker and rebuilds.

## Which model and dimension should I choose?

Start with the default, and step up only if relevance on your own corpus falls short. Model choice moves both latency and storage: the cosine scan does work proportional to __dimension × chunk count__, and the file grows linearly with the dimension.

The default, `fastembed:minishlab/potion-multilingual-128M`, is a 256-dimension static [Model2Vec](https://github.com/MinishLab/model2vec) model: it embeds a query in ~0.1-0.3 ms, keeps the file smallest, and serves multilingual documentation. A contextual (transformer) model such as the MiniLM, mpnet, or e5 tiers ranks better on nuanced or ambiguous queries, at the cost of a larger vector, a larger file, a slower scan, and a much slower embed, which then dominates both query time and indexing time.

Measured candidates (embed p50 over 20 iterations; `hit@k` is a small fixed multilingual relevance sanity check, not a full benchmark; produced by `scripts/benchmark_embedders.py`):

| Model | Dimensions | Embed p50 | hit@1 | hit@3 |
| --- | --- | --- | --- | --- |
| `fastembed:minishlab/potion-multilingual-128M` (default) | 256 | 0.1 ms | 0.80 | 1.00 |
| `fastembed:sentence-transformers/paraphrase-multilingual-MiniLM-L12-v2` | 384 | 4.2 ms | 0.80 | 1.00 |
| `fastembed:sentence-transformers/paraphrase-multilingual-mpnet-base-v2` | 768 | 11.2 ms | 0.80 | 1.00 |
| `fastembed:intfloat/multilingual-e5-large` | 1024 | 35.6 ms | 0.80 | 1.00 |
| `fastembed:BAAI/bge-small-en-v1.5` | 384 | 4.0 ms | 0.80 | 1.00 |
| `fastembed:BAAI/bge-large-en-v1.5` | 1024 | 35.2 ms | 1.00 | 1.00 |
| `hf:onnx-community/Qwen3-Embedding-0.6B-ONNX` | 1024 | 44.1 ms | 1.00 | 1.00 |
| `hf:onnx-community/embeddinggemma-300m-ONNX` | 768 | ~23 ms | 0.80 | 1.00 |

The two `hf:` rows run through the generalized Hugging Face loader. Qwen3-Embedding is a decoder-style export with external weights; at 1,024 dims and ~44 ms it is the slowest and largest option, and the only one to reach `hit@1` 1.00 on the multilingual bank. EmbeddingGemma bakes pooling and its projection heads into the graph, and the loader reads that final output directly; reading the raw backbone instead drops `hit@1` to 0.60. Measure on your own corpus before trading the default's size and speed for a larger model.

## Why brute force, not an ANN index?

Because at this scale an approximate-nearest-neighbour index buys no speed and gives up exact results. Measured over 1,000 chunks with the DuckDB `vss` extension (HNSW, cosine metric), at the earlier 384-dim default, against the exact top-k as ground truth:

| Approach | Vector-ranking p50 | Recall@5 |
| --- | --- | --- |
| Brute-force exact scan | ~30.1 ms | 1.00 |
| HNSW index (`vss` extension) | ~29.6 ms | 0.96 mean, 0.80 worst-case |

The query plan confirmed `HNSW_INDEX_SCAN`, so this was a genuine HNSW path: ~2% faster, within noise, for 4% lower mean recall. HNSW also needs DuckDB's experimental index-persistence flag. Even at 100,000 chunks the exact scan answers in about a tenth of a second, so the default stays exact. The schema is HNSW-ready — a fixed-size `FLOAT[dim]` array column — for anyone who outgrows that range.

## What does the package deliberately leave out?

Two things, both scope choices that keep it small rather than missing features.

__No stemmed, multi-field full-text engine.__ The embedding model is the primary relevance signal, and it already handles paraphrase and synonyms across languages. The keyword signal is a language-agnostic exact-token BM25, with no stemming and no stopwords, present only to catch what vectors miss: acronyms, codes, and identifiers, so a query for `ESRS` finds `ESRS`.

__No re-ranking stage.__ Retrieval returns the fused top-k directly; there is no cross-encoder or LLM re-ranker. A re-ranker adds a second model, possibly a network hop, and latency, for a modest gain the hybrid fusion already covers for the target use case. A harness that needs one is free to add it.

## When is a network vector database the better fit?

When the corpus outgrows what an exact scan serves well, far beyond the hundred-thousand-chunk range measured here. Below that, a hosted vector database pays a network round-trip on every query, an estimated ~10-50 ms same-region and 50-150 ms or more cross-region or on a cold connection, with a long tail, and none of that time does any searching. In-process retrieval answers in ~26 ms at 1,000 chunks and ~105 ms at 100,000, with no hop at all. The sweet spot for `duckdb-vectors` is integrating thousands to tens of thousands of chunks directly into the agent, trading a managed vector service for a file in the image.

## How did these numbers change?

Most of them improved by fixing one measured cost at a time. The before and after values below were measured on the same MacBook Pro M1 (2021) when each change was made, and are kept here to show which changes paid off:

| Change | Before | After | Source |
| --- | --- | --- | --- |
| Re-indexing an unchanged folder writes nothing | 16-18 s, file held throughout; queries from another process 0/10 | ~1 s, file held 0.02 s; 25/25 | v261102 |
| One DuckDB connection for every Markdown file of a run | 7.8 s to chunk 247 files | 0.9 s | v261102 |
| Connect on first use and retry a lock conflict | two MCP servers on one file: 15 and 0 queries succeed | 15 of 15 each | v261102 |
| The MCP server keeps the embedding model loaded | ~1.25 s per later search | ~45 ms | v261103 |
| Rebuild the keyword index once, not on every write | 110 s to write 50,000 chunks | 93 s | Unreleased |
| One `DELETE` and one `INSERT` per batch, not two statements per chunk | 93 s to write 50,000 chunks; first index of the real corpus 17.7 s | 19.7 s; 3.6 s | Unreleased |
| Default model: 256-dim static instead of 384-dim contextual | 1,000-chunk file 9.5 MB; query embedding ~4.4 ms | 4.5 MB; ~0.3 ms (same benchmark) | v261024 |

The Source column names the release in [CHANGES.md](https://github.com/bernard357/duckdb-vectors/blob/main/CHANGES.md) that records each change. The model row compares two figures measured with the same earlier benchmark script; the 4.8 MB of the first table comes from the current script, whose synthetic chunks differ slightly, so do not compare it with the 9.5 MB.

One change is worth a note, because the projection behind it was wrong. Rebuilding the keyword index on every write looked like the cost that made large builds slow: timings at 2,000 and 6,000 chunks grew faster than linearly, and a curve through them projected ~22-25 min to build 100,000 chunks, against ~3-4 min with a single rebuild. Measured afterwards, one rebuild over 50,000 chunks takes 0.09 s; the real cost was the row-by-row writes, at ~1.6-2 ms per chunk, so deferring the rebuild gained only 10-20%, and batching the writes made them about five times faster. Deferring the rebuild also needed a safeguard: a row written after the last rebuild was missing from keyword search without any error, so writes now mark the index stale in the database file and the next keyword search rebuilds it. Profile the stage that costs the time before projecting a gain.

## How much do tags improve retrieval?

> __Superseded, under revision.__ The figures in this section and the next come from validation sets that could not show what tags restore: questions written from one passage alone, a single golden chunk per question, an engineering-pages baseline already near its ceiling, and gains on public sets where the query names the tag value. They are kept for the record and are being redone in [issue #65](https://github.com/bernard357/duckdb-vectors/issues/65). Read the H1, H4 and H5 verdicts below as provisional.

__It depends on whether queries use the words the tags carry.__ Over four datasets and five embedders, tagged retrieval raised hybrid Pass@20 by up to +0.19 where queries name the tag values (SEC filings), by +0.01 to +0.05 on news articles and engineering pages with the default static model, and by nothing on code, where queries never name a repository. With two small transformer models it also lowered Pass@20 on two corpora, by 0.03 and 0.02. On the full MultiHop-RAG set of 2,255 questions the default model gains +0.034 [+0.027, +0.041] with both. The tags are `company`, `year` and `section` for the filings, `title`, `source`, `category` and `published` for the news, `topic` and six model-derived fields for the engineering pages, and `repo`, `directory` and `extension` for the code. The comparison has 42 cells and no correction for multiple comparisons, so a lone star on a small difference is weak evidence. The large gains and the losses on MiniLM and bge-small are not.

| Hypothesis | Verdict | Evidence |
| --- | --- | --- |
| H1. Tags reduce failure at 20 on tag-rich corpora | Holds when queries use the tags' words, and can hurt when they do not | Gains on filings, news and engineering pages with the default model, none on code, losses of 0.02 to 0.03 for MiniLM on engineering pages and bge-small on news |
| H2. Gains are larger for small static embedders | Not supported | Larger for the static model on news and engineering pages, but about a third as large on filings (+0.051 against +0.140 and +0.177). The two large embedders ran on the code set only, where nothing helps, so they say nothing |
| H3. Tagged keyword search adds on top of tagged embeddings | Partly | Adds +0.011 to +0.025 on news with all three embedders and +0.029 on filings with the default model. Adds nothing on code, on engineering pages, or on filings with the transformers, where the embedding already carries the tags |
| H4. Tags recover at least half of an LLM contextual header's gain at about zero cost | Not supported | See below. Native code tags recovered none of it |
| H5. Corpus statistics predict which tags help | Not for embedding separation, yes for query mentions | See [Which tags help?](#which-tags-help) |

__H4 reference.__ Anthropic's Contextual Retrieval, with Claude Haiku 4.5 writing a context for each of the 737 code chunks from its whole file, raised hybrid Pass@20 on the code set by +0.078 [+0.041, +0.118] with the default model, +0.123 [+0.081, +0.166] with MiniLM and +0.056 [+0.030, +0.085] with bge-small. The `repo`, `directory` and `extension` tags, together, gained -0.011, -0.001 and -0.006 with the same three embedders on the same queries. They recover none of it, because the questions about code never name a repository or a path. The context went in as a `context:` line in front of the chunk, and in the keyword index in the last condition, so it follows the same path as a tag. The comparison says nothing about tags that queries do name, and the reference run did not use Claude 3 Haiku as the original did. It costs one model call per chunk, with the file in each prompt, where tags cost nothing at index time.

__Prefix or suffix?__ For a transformer, the order is decisive. With MiniLM, tags placed before the chunk moved vector-only Pass@20 by +0.208 [+0.155, +0.266] on filings, -0.102 [-0.140, -0.064] on engineering pages and -0.095 [-0.141, -0.053] on code. The same tags placed after the chunk moved it by -0.011, 0.000 and -0.004: that is, the suffix is almost ignored, which keeps the model from the losses and from the gain. In hybrid search the gap on filings is +0.142 against -0.002. MiniLM was trained on 128 tokens and may simply not read text that far into a 300-word chunk. The default static model averages token vectors, so order cannot matter for it, and its prefix and suffix runs differ only when truncation cuts the suffix: -0.005 [-0.014, +0.002] on news and nothing elsewhere. The prefix is what the benchmark tested for gains, so the prefix stays, as in the published work, and a user whose embedder loses with tags can check the suffix.

__What the datasets are.__ The code set is the Anthropic cookbook's 737 chunks and 248 questions, used as published. The filings are 25 SEC 10-K filings re-chunked like the dataset's own script into 4,490 chunks, with 117 questions whose ground truth is the chunks cited by a RAG pipeline's answer, so it is not a human judgement. The news set is 609 articles in 4,303 word-window chunks, with each quoted fact of a question mapped to the chunks that contain it. The engineering pages are 252 pages in 5,293 chunks, with two questions generated by Claude Haiku 4.5 from each of 400 passages, kept after dropping those that copy more than four consecutive words, and 500 sampled for the runs. Generated from the passage alone, those questions need no tag to be answered, which understates what tags give. That corpus is private: only its results are published. Runs are single and deterministic apart from timing. The large embedders took about 800 ms per chunk on this machine, which is why they ran on the code set alone.

## Which tags help?

> __Superseded, under revision.__ See the note at the top of the previous section. The 20% query-mention threshold was fitted on the 17 tags it is compared with here, and nothing was held out.

__Not the ones that separate documents best, but the ones queries name.__ A leave-one-tag-out run (all tags, minus one) over 17 tags in four datasets, with the default model, gives each tag's contribution to hybrid Pass@20. Two tags carry most of the gain: the company name for filings (+0.040) and the news source (+0.031). The table lists them with the statistics of the `tags` report:

| Dataset | Tag | Queries mentioning | Document d lift | Verdict | Contribution to Pass@20 |
| --- | --- | --- | --- | --- | --- |
| Filings | company | 1.00 | +0.02 | effective | +0.040 [+0.016, +0.068] * |
| | year | 0.93 | +0.03 | effective | +0.009 [+0.000, +0.019] |
| | section | 0.00 | +0.01 | decorative | -0.001 [-0.012, +0.009] |
| News | source | 0.99 | +0.03 | effective | +0.031 [+0.018, +0.044] * |
| | published | 0.00 | +0.03 | decorative | +0.010 [+0.003, +0.018] * |
| | title | 0.00 | +0.35 | decorative | +0.009 [-0.003, +0.021] |
| | category | 0.22 | +0.02 | effective | +0.005 [-0.000, +0.011] |
| Engineering | topic | 0.51 | +0.27 | effective | +0.012 [+0.000, +0.026] |
| | six derived fields | 0.00 to 0.08 | +0.04 to +0.15 | decorative | -0.008 to +0.008 |
| Code | repo, directory, extension | 0.00 to 0.01 | +0.01 to +0.06 | decorative | -0.015 to -0.004 |

The embedding separation lift, which measures how much a tag pulls the chunks of one document together, has a rank correlation of -0.03 with the contribution over the 17 tags. A variant that groups chunks by tag value instead of by document gives -0.12. Both rate the company and the source as decorative, and the title, whose lift is +0.35, as the best tag. The share of queries that contain one of the tag's values has a rank correlation of 0.62. That is why `duckdb-vectors tags` decides on coverage, entropy and, given a file of queries, that share, and reports the separation without using it.

The rule marks a tag decorative when under 20% of the queries mention a value. It agrees with the runs on 13 of 17 tags, counting a tag as helping when its interval excludes zero. It misses the news `published` date, which helps a little (+0.010) with no query naming a date, and it calls three tags effective whose gain is not significant (`topic`, `category`, `year`). The 20% threshold was set on these 17 tags, so it fits them by construction. The two tags written into the private engineering pages, `programming_language` and `operational_domain`, were chosen by the separation statistic and show no contribution here (-0.008 and 0.000), but the questions were generated from passages alone and cannot name a tag. A rule that fits its own calibration set proves little, and the next corpus is the test. Near-unique tags such as the title and the published date did no harm when left in, which is why a value shared by about one document each produces a note and not a verdict.

## What does tagging cost?

__Nothing measurable at index time, and a few percent of file size.__ Embedding time per chunk with tags is within the noise of the baseline for every embedder, because a prefix of a few words adds few tokens, and the search time is the same. A 50-word LLM context is not that cheap to embed: it made bge-small 31% slower (69 to 91 ms per chunk), on top of one model call per chunk to write it.

| Embedder | Embedding, baseline | Embedding, with tags | Query embedding | Search, p50 |
| --- | --- | --- | --- | --- |
| potion-256 | 0.2 to 0.3 ms per chunk | 0.2 to 0.6 ms | 0.1 to 0.3 ms | 29 to 42 ms |
| MiniLM-384 | 21 to 29 ms | 21 to 22 ms | 4.6 to 13 ms | 25 to 37 ms |
| bge-small-384 | 69 to 114 ms | 74 to 108 ms | 4.6 to 12 ms | 24 to 36 ms |
| e5-large-1024 | 804 ms | 827 ms | 44 ms | 28 ms |
| bge-large-1024 | 799 ms | 841 ms | 41 ms | 26 ms |

Embedding times come from a fresh embedder on 100 chunks of each condition, because runs share vectors between conditions. The search time excludes the query embedding, which the table lists, and is the median of the hybrid search at top 5, 10 and 20. The index file grew by 0 to 9% with tags, up to 17.8 MB from 17.1 MB on the news set, and 17.1 MB from 15.7 MB for bge-small on engineering pages, since tags add a column and, with keyword matching, a longer keyword index. A set of tags whose words overflow the model's window costs relevance instead: the `tags` report warns when it estimates that prefix and chunk exceed it, and for 137 of the 5,293 engineering chunks it did with the default model.

## How to reproduce these numbers?

Run the benchmark scripts from the repository root with the project venv. Each prints a table in the format used on this page and can write raw results with `--json`.

```shell
$ .venv/bin/python scripts/benchmark_queries.py                    # query latency and file size at 1k, 10k, 50k, 100k chunks
$ .venv/bin/python scripts/benchmark_queries.py --backend hashing  # the scan curve alone
$ .venv/bin/python scripts/benchmark_indexing.py                   # first index, restart, one-file edit on a synthetic folder
$ .venv/bin/python scripts/benchmark_indexing.py --folder /path/to/your/docs
$ .venv/bin/python scripts/benchmark_embedders.py                  # the model comparison
$ make bench-tagged BENCH_ARGS="--dataset multihop --sample-queries 500 --ablate --suffix"  # tagged retrieval
$ .venv/bin/python -m benchmarks.tagged_retrieval.analyze          # the tables of the tagged retrieval sections
```

The tagged retrieval benchmark downloads its public data on first use, writes one JSON file per run keyed by git SHA, and is described in [its README](https://github.com/bernard357/duckdb-vectors/blob/main/benchmarks/tagged_retrieval/README.md). `benchmark_queries.py` builds synthetic indexes of ~300-word chunks drawn from a letter-only vocabulary, so the keyword index holds real tokens. `benchmark_indexing.py` generates its Markdown folder from a fixed seed. The MCP and multi-session figures come from the server's own tests and stdio probes against the real corpus.
